#     pip install -r requirements-tabarena-git.txt
#
# GOTCHA (confirmed live, RamanICL/HTW, 2026-10-01): if the env already has ANY
# tabarena install reporting the same version string (e.g. the old `0.1.0` PyPI
# placeholder mentioned above), a plain `pip install -r requirements-tabarena-git.txt`
# silently no-ops -- pip matches on version string, not on git URL/commit, so it
# considers the requirement already satisfied and skips it. Exit 0, no warning, and
# you're left on whatever tabarena was already installed (confirmed: a different
# REPOSITORY entirely, `autogluon/tabarena` instead of this fork). `pip show tabarena`
# reports `0.1.0` identically either way and will NOT catch this -- check
# `site-packages/tabarena-*.dist-info/direct_url.json`'s `url`/`commit_id` instead, or
# just use `pip install --force-reinstall -r requirements-tabarena-git.txt` whenever
# provisioning into a non-fresh env.
#
# Related, observed in the same incident: `--force-reinstall` on tabarena alone (not
# the whole raman-bench[models] stack) can pull its own transitive torch version,
# independent of the torch~=2.14/torchvision>=0.29.0 pairing this package's own
# pyproject.toml deliberately maintains (see pyproject.toml's torchvision comment --
# torchvision's PyPI metadata pins its required torch version exactly, so any drift
# between the two breaks torchvision's C-extension import). If you `--force-reinstall`
# tabarena into an existing env, re-check `torch`/`torchvision` versions afterward
# (or re-run `pip install raman-bench[models]` to let its own pins win) rather than
# assuming they're untouched.

# tabicl -- pinned to an EXACT version, not left floating on tabarena's own
# `tabicl` extra (`tabicl>=2.0.0`, unbounded upward). Flagged by a downstream
# consumer (RamanICL): a TabICL checkpoint carries its architecture config,
# splatted into `TabICL.__init__` at load time -- a build that doesn't
# recognize a key the checkpoint was trained with hard-fails
# (`TypeError: ... got an unexpected keyword argument ...`), or worse, if the
# mismatch lands on a key with a default, silently changes the architecture
# instead of erroring. TabArena's own TABICLV2 baseline uses an official,
# PyPI-released checkpoint (not a bleeding-edge retrain), so this specific
# failure mode isn't known to be live for us today -- but an unbounded floor
# means a future `pip install --upgrade` could silently pick one up with no
# warning, exactly the risk flagged. Pinned to 2.2.0, the version already
# confirmed running in production (verified live on a real cluster pod) --
# not a guess at some other "safer" version.
tabicl==2.2.0
